Memory Manager

Resume

This project has been based on understanding the basics of memory management and how to implement a memory manager/allocator. To understand this I have developed a free list allocator. With a basic operation and with a single memory pool. This allocator is developed to be used in single thread so it does not support multiple threads and therefore does not optimise access at chache line level and does not provide a safe memory allocation.

Memori Manager Development

The memory manager/allocator is based on the management of a previously allocated memory pool. For this purpose, two hash tables have been created where the freed and reserved pointers are stored. Using as a key the pointer and as a value the information about that pointer, such as the size it occupies.

To reserve memory, the memory manaller looks for a block that is greater than or equal to the requested size. If it finds a larger size it splits the block in two, storing one in the freed table and the other in the allocated table and returning the pointer. If nothing is found, null is returned.

For the freeing of memory it is necessary to make more steps since the big block will be split in multiple small blocks and it is necessary to put them together again. To do this, you take the information from the pointer that is being freed and check to see if it has adjacent blocks that are freed. For the block in front of you, just check to see if my memory address plus my size is free. For the block in front of you, just check to see if my memory address plus my size is free. Once found, check if the memory address plus its size is equal to the memory address you are trying to free.

Once this is done, the blocks are put together and stored in the freed list.

What I have learned

Memory management is complex to the point of affecting execution time, not just the time it takes to allocate memory or free it. So I would divide what I have learned into three points.

Allocators:

First of all, the type of allocator you are using matters when it comes to allocating memory, as there is no perfect allocator for all situations. There are allocators like the following with their pros and cons.

  • Linear Allocator
  • Stack Allocator
  • Free List Allocator
  • Bitmap Allocator
  • Buddy Allocator
  • Global Allocator

It should be noted that a global allocator is not an allocator that follows any memory reservation paradigm but is important to mention because of its ability to be accessed by multiple threads.

Multithread:

Taking into account that most systems where memory management is important are multithreaded, it is necessary to adapt the allocators for multithreading. This implies both safe access to the allocator and taking into account where the memory is being reserved, as there may be synchronisation of threads if they read or write in nearby positions (within the same chache line). This happens because CPUs do not read a single value from the ram but load a chache the size of a chache line (in most cases 64 bytes), at least at the L1 level.

Hardware Resources:

Finally, it is worth noting that the concept of memory that is often used in the teaching of C/C++ is that memory comes from RAM. This is not exactly the case. Taking into account that most operating systems have virtual memory. That is to say that one works with virtual memory that is mapped to physical memory (RAM). You should make good use of these resources and not hog them. Because many of the allocators mentioned above work with large memory pools. For this purpose, a range of virtual memory addresses are reserved and mapped or unmapped to physical memory according to their usage.
